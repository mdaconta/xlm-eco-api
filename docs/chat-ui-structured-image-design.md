# XLM Chat verification UI follow-up

Status: Design Gate passed with findings and Quality Gate passed on 2026-09-16. Scope: expose the committed Increment 3A one-image structured inference in the existing Flask/Socket.IO chat UI so a user can verify the remote path interactively. This does not add image generation, local VLMs, provider switching, or a new XLM RPC.

## Existing behavior and change

`gui/chat-ui/app.py` registers one gRPC client on startup and uses the configured provider/model for text `asyncChat`; `index.html` has only a text prompt and streaming result area. Keep this text route and Socket.IO behavior. Add an **Analyze image** mode with one file picker, instructions, and an editable JSON Schema (default: an object with a required `description` string). Show the selected image preview, MIME and size before submission. Label the configured provider/model.

The browser posts multipart form data to a new `/analyze_image` Flask route. The route accepts exactly one image, nonblank instructions, and an object JSON Schema; it rejects unsupported MIME, missing/oversize media and overlong text/schema before gRPC. Limits align with the XLM contract: 3 MiB image and 64 KiB each for instructions and schema. Flask caps the complete HTTP request at 4 MiB and reads at most 3 MiB plus one byte from the uploaded file before rejection. It builds `StructuredImageRequest` with the existing registered `client_id`, CLI-configured provider/model and explicit MIME/bytes, then calls `generateStructuredImage` with a 90-second deadline. The response contains success/status, structured JSON, provider/model, and normalized error code/message/retryability/HTTP status. The UI displays those fields as text, including failures, without interpreting provider-specific raw bodies. The application does not retain the upload; Flask may use bounded temporary multipart buffering.

This UI is for local verification. Bind Werkzeug to `127.0.0.1` and disable debug mode. Generate a random per-run token, render it into the same-origin page, and require it in an `X-XLM-UI-Token` header for both POST routes; browser JavaScript supplies the header. This prevents an unrelated page from issuing unauthenticated local POSTs that consume provider quota. Do not log the token, image bytes or new image instructions. This does not establish a network-facing admin or multi-user security model.

Move command-line parsing and live gRPC registration behind the `__main__` startup path, leaving a small module-level seam where a focused test can inject a fake stub and client settings without contacting a provider. A `grpc.RpcError` from the image route returns a short JSON transport error with only a safe status name (`UNAVAILABLE` or `DEADLINE_EXCEEDED`) and HTTP 502/504; no raw gRPC details are returned. Normalized XLM application failures remain a separate HTTP 200 result with their own error fields.

## Verification

Use a focused Flask route test with a fake gRPC stub to verify multipart construction, MIME and schema propagation, response metadata/error mapping, invalid input rejection, token enforcement, and preservation of `/send_message`. Run `mvn verify` for the XLM backend baseline. For live verification, start the packaged gRPC server with the configured remote key and trusted TLS roots, start the chat UI with `openai gpt-4o-mini`, then upload a generic image and instructions/schema. Confirm the visible preview, structured output, provider/model identity and error behavior; test a text chat in the same UI. A Flask fake-stub test does not replace the already recorded real remote XLM acceptance or the user's live browser check.
