# Increment 3A: existing XLM review and gap analysis

Date: 2026-09-16. Scope: the checked-out `xlm-eco-api` repository before Increment 3A implementation. The working tree already has an unrelated deletion of `python_client/generated/.gitkeep`; this review does not adopt it.

## Baseline architecture and operation

- One Java 17 Maven module owns a proto3 gRPC service, server implementation, provider interfaces and adapters, plus a separate vector service. Protobuf and gRPC Java sources are generated by Maven. Java, Python and Node sample clients consume the same contract: Java uses generated Java types, Python uses Maven-generated `python_client/generated` stubs, and Node loads the `.proto` at runtime.
- `XlmEcosystemServiceImpl` registers clients in memory, selects a preferred provider by capability, and delegates `syncChat`/`asyncChat` to `ChatProvider`. `ChatRequest` already contains `prompt`, `provider`, `model_name` and optional `LmParameters`, but the server's text path uses the selected capability mapping rather than enforcing `request.provider`. `ChatResponse` contains only completion text. The existing OpenAI adapter sends text to Chat Completions and extracts `choices[0].message.content`; it returns HTTP failures as a completion string. Other adapters implement text/embedding capabilities. Provider discovery uses `ServiceLoader` and configuration prefixes.
- `GenerativeProvider` publishes coarse provider capabilities; there is no model-level metadata or structured-output capability. Registration, provider selection and error behavior vary by method. The server currently logs the entire loaded `Properties`, which can expose configured API keys and must be corrected before remote acceptance.
- No `src/test` tests or configured test framework exist. The README documents Maven build, config, server, and Java/Python/Node sample client commands; `config.properties` is ignored. Maven invokes Node installation and Python dependency/stub generation. The Node client dynamically loads the proto. The repository has no release automation documentation beyond its Maven package/shaded JAR guidance.

## Capability comparison

| Increment 3A capability | Baseline | Minimum change |
| --- | --- | --- |
| Text plus exactly one image over gRPC | Missing | Add one unary method and dedicated general-purpose messages. |
| MIME and media representation | Missing | Bounded inline image bytes with explicit MIME; document limit and supported formats. |
| Explicit provider/model | Partial | Existing `ChatRequest` fields; new method must enforce both against a loaded adapter and supported model. |
| Structured-output request | Missing | Require a caller-supplied JSON Schema object for the new method. |
| Normalized structured response | Missing | Return validated JSON payload and explicit status/error, separate from raw diagnostics. |
| Provider/model response identity | Missing | Return selected provider and actual model identity. |
| Meaningful provider/model errors | Conflicting | Text path often encodes errors in completion; new path needs stable error codes, retryability and safe diagnostics for invalid selection, HTTP failure, timeout and malformed output. |
| Existing text-client compatibility | Partial | Preserve all existing RPCs, message fields and numbers; regenerate stubs and run existing client compatibility checks. No current automated baseline exists. |

## Compatibility, tests and prerequisites

- Additive RPC/messages avoid breaking protobuf wire compatibility. Existing generated clients can continue to call existing methods; regeneration adds the new method. No `ChatRequest` or `ChatResponse` field numbers should change. The service remains package-less as in the baseline to preserve method paths.
- Isolate the new vision operation behind a small provider interface and implement it in only the OpenAI adapter. Reuse the server's configured provider map. Keep the existing text behavior intact except removing credential-bearing startup logging.
- Tests are needed for old text wire usage, new construction/validation, MIME and schema propagation, explicit provider/model enforcement, normalized success and error paths, malformed provider output, Java/Python/Node stub consumption, and a real remote image request. A mock-only result is insufficient.
- Prerequisites: a configured OpenAI key, reachable Chat Completions endpoint, an image/structured-output capable selected model, Java/Maven/Python/Node toolchains, and a generic test image. Key presence was checked without reading it into task output. Actual remote access and model availability remain to be demonstrated.

## Blocker assessment

No breaking protobuf, cross-language, provider-boundary or architecture decision is currently required. The credential logging defect is a prerequisite fix within the server code touched by this increment. The bounded design and Mentor Design Gate must precede production changes. Remote operational acceptance remains contingent on an actual successful provider call.
