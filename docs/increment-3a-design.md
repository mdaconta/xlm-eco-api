# Increment 3A: bounded multimodal design

Status: proposed for Mentor Design Gate, 2026-09-16. Source requirements: Video Inventory's Increment 3A sections in its Implementation Plan and XLM Upgrade Plan. XLM remains domain-neutral.

## Contract and compatibility

Add `generateStructuredImage(StructuredImageRequest) returns (StructuredImageResponse)` to the existing service. Keep every existing RPC and field unchanged. New request fields: `client_id`, nonblank `instructions`, required `ImageInput` (`mime_type`, inline `bytes data`), nonblank `provider`, nonblank `model`, and required `json_schema` string containing a JSON Schema object. One singular image field makes multiple images impossible in this version. The schema describes the requested JSON result; caller instructions carry domain semantics. XLM strictly parses request schema and provider output as JSON objects, then serializes the result as valid JSON. Full schema conformance relies on the provider's strict output mode.

Inline media is accepted only for `image/png`, `image/jpeg`, or `image/webp`; bytes must be nonempty, no larger than 3 MiB, and match the declared format signature. Instructions and schema are each limited to 64 KiB of UTF-8. This keeps a complete request below the default 4 MiB gRPC Java inbound limit, including protobuf overhead. Larger media references and streaming are future work. The adapter base64-encodes bytes in an OpenAI data URL only after validation.

New response fields: `json_payload` (a syntactically valid JSON object on success), `provider`, `model` (the model reported by the provider, with selected model retained if the provider omits it), `success`, `status` enum (`STATUS_UNSPECIFIED=0`, `COMPLETED`, `FAILED`), and `error` (`code`, safe `message`, `retryable`, `provider_http_status`). Error codes distinguish invalid request, unsupported provider/model, authentication, rate limit, timeout, provider unavailable/failure, malformed provider response and invalid structured output. Failure responses include the requested provider/model identity where known. Do not place raw provider bodies, API keys, image bytes or prompts in errors or logs. gRPC transport errors are reserved for unexpected server faults.

The new method is version 1 of this contract; existing proto service paths and text message tags remain stable. Old Java/Python generated stubs remain wire-compatible, newly generated stubs expose the new method, and Node's runtime loader sees the additive RPC. No changes to sample client command-line interfaces are required.

## Server/provider responsibilities

The service validates registration, required fields, media and schema syntax before provider invocation. It resolves `provider` from its configured provider map, requires an image-capable adapter and an explicitly allowed model. Selection is per request: no fallback, routing chain, or persistent preference change. A small `StructuredImageProvider` interface accepts a provider-neutral validated request object and returns provider-neutral output or typed failure.

Only `OpenAIProvider` implements the interface. Its configured `vision_models` list is a small explicit model allowlist (default `gpt-4o-mini`), representing the model capability gate for this increment; an unlisted model fails locally. It posts to the existing configured Chat Completions URL with one user text part and one `image_url` data URL, plus `response_format: {"type":"json_schema","json_schema":{"name":"xlm_result","schema":<caller object>,"strict":true}}`. It reads `choices[0].message.content`, checks normal finish/refusal conditions, parses an object JSON payload, and captures response `model`. Supported schema subset is ultimately provider-defined; an unsupported schema produces a normalized provider error. No client supplied URL is used.

HTTP mapping: 401/403 authentication; 429 with a known quota/spend error code is nonretryable provider quota, while other 429s are retryable rate limits; 408/504 and transport timeout retryable timeout; 5xx retryable provider unavailable; other non-2xx provider failure. Parse a bounded provider error code for quota classification; a validated short ASCII code or type may also appear alongside a fixed local error message for diagnosis. Never echo the raw response body or its free-form message. Malformed 2xx provider envelopes or invalid JSON content are nonretryable malformed response/output. The service maps typed failures to its response error fields. For structured-image calls, bound the HTTP read timeout to 120 seconds and the total call timeout to 150 seconds so detailed image responses can complete while a stalled provider remains bounded. For this workstation/provider path, use HTTP/1.1 only for the structured-image client: the same 3.24 MB Astra request, key, and payload returned HTTP 403 `model_not_found` through Java OkHttp over HTTP/2, but HTTP 200 with 16 findings through Java OkHttp over HTTP/1.1 and through PowerShell. This is an observed compatibility workaround, not a general OpenAI API requirement; re-evaluate it when the provider path or OkHttp runtime changes. The compared JSON request was 3,235,847 bytes (SHA-256 `5768369011DC0B86785473784D822DBAD14C9CD367D583A44FBA0D5DFD674127`) on Java 21.0.12 and OkHttp 4.9.3; both Java attempts used the same key and request body. The HTTP/2 attempt returned 403 `model_not_found`; the forced HTTP/1.1 attempt returned 200 with 16 findings. Per-attempt elapsed times were not retained. This request hash permits later comparison without storing the image or credential in this design record. The ordinary chat and embedding client retains its existing protocol negotiation. Bound response-body size. Replace the existing server startup log of full configuration properties with a safe summary of non-secret names/counts.

## Verification and acceptance

Add focused Java tests using an in-process service and local fake HTTP endpoint, covering all request validation, provider/model selection, OpenAI JSON construction and MIME propagation, schema forwarding, success normalization, each material failure class, malformed provider envelopes and text-only method preservation. Run `mvn test`/`mvn verify`, Python stub generation/import and Node proto-loader compatibility. Test old text message serialization against the updated proto. Send an actual network gRPC request near the accepted 3 MiB image boundary to confirm the default transport limit; reject oversized instructions/schema before transport where feasible. Do not treat generated stub compilation alone as a real remote acceptance test.

Run one real gRPC-to-OpenAI call using a generic image, explicit `openai`/`gpt-4o-mini`, a small object schema and visual instructions. Record only non-secret request metadata, structured output, provider/model, elapsed time, a safe error example, and text-only compatibility. No credentials or image data in durable evidence.

Official OpenAI references used for the adapter shape: [image inputs](https://platform.openai.com/docs/guides/images-vision), [Chat Completions structured outputs](https://platform.openai.com/docs/guides/structured-outputs), and [Chat Completions API](https://platform.openai.com/docs/api-reference/chat/create). The design relies on the existing configured endpoint rather than adding a new SDK or switching API families.

## Proposed later increment: local VLM and administration

The Architect's 2026-09-16 clarification keeps local VLM execution and provider switching outside Increment 3A implementation. A later design should let a local VLM implement the same `StructuredImageProvider` contract, returning the same normalized response and errors. Model identity and capability checks remain explicit; the local adapter must not silently replace a requested remote model.

A small admin application can use dedicated gRPC management commands to list configured VLMs and capabilities, inspect active configuration, validate a local or remote model configuration, and explicitly activate a model for future requests. The server should own configuration authority and persist validated changes atomically; the admin app should be a client, not a second configuration store. Management RPCs require authentication/authorization and must never return API keys. Define the scope, configuration storage, authentication, transition behavior for in-flight requests, and rollback/error semantics in that later increment's Design Gate. Increment 3A's per-request explicit provider/model selection remains unchanged and does not implement activation or switching.
